# Frontend Architecture

## Runtime

The frontend is a Vue 3 + Vite application. Chat execution is driven by the session WebSocket and Pinia stores. ECharts renders chart presentations.

## Chat Keyboard Input

The chat composer and message editor use Enter to send or submit and Shift+Enter to insert a newline. Enter during IME composition keeps the browser's native candidate-confirmation behavior. Default prevention belongs in the submit handler after these guards, so template event modifiers cannot swallow newlines or IME confirmation. The message editor retains Escape to cancel and ignores submissions while a request is pending.

## Default Model Resolution

The model and thinking selectors resolve the effective default through `/api/agent/runtime-core/status`, scoped by team and entry Agent. The frontend preserves the model's `source` and `fallback_reason`: a broken Agent default tier shows a warning next to the model selector, explains the system-model fallback in its menu, and offers administrators an Agent configuration link. Normal inheritance from the system configuration has no warning; an explicit model selection hides the default-tier warning. Missing references are never presented as available models.

Resolution requests share a bounded cache with a 30-second TTL. Successful Provider, Agent, team and system configuration mutations, or Agent draft publication, invalidate it and refresh mounted selectors. Failed mutations preserve the cache. A response started before invalidation resolves against the current cache rather than restoring the old configuration; component request sequences also prevent late responses from replacing a newer team/Agent selection. Opening the model menu retries unavailable resolution and refreshes expired results.

## Markdown Rendering Safety

Raw Markdown HTML remains disabled. Custom code-block headers escape language names in both their visible title and copy-button attributes, including file code previews. Code highlighting and the encoded original copy payload retain their existing behavior. Regression tests include malicious fence language tags and attribute-breaking language strings.

## Long Conversation Updates

`ChatMessageList` computes retry targets in one forward pass over visible messages. Agent-authored and non-revisable user messages remain barriers, so retry cannot silently target an older human turn. Root message membership uses a computed ID set shared by editing and retry eligibility. These indexes depend on message identities and permissions rather than streamed body text, and are reused during hover updates.

`MarkdownContent` keeps canonical message content immediate but limits append-only streaming HTML updates to one parse per 80ms. The first nonempty chunk, replacement or shortened text, and stop/completion state render immediately; completion removes the streaming cursor and flushes the full final text. Pending callbacks are cancelled on replacement and unmount. Static messages and code-copy payloads keep their existing behavior.

The root conversation enables `useMessageWindow` after reaching 200 visible messages. It shares the existing outer scroll container with the composer and approval UI; short conversations and workbench threads keep their existing rendering. A keyed height layout and 900px overscan on either side mount only nearby rows, the last two rows, and any edited, expanded or focused rows. Spacer heights include the original leading gaps. ResizeObserver updates dynamic heights and preserves the reader's message/offset, or the bottom when following; width changes invalidate height estimates. Measurements, observers and event listeners are disposed with the view. Conversation changes reset the height cache and display mode. Message data and retry indexes still cover the complete conversation.

`ChatMessageList.scrollToMessage` accepts a visible-list index, stable message key/ID, or `seq:<number>` and mounts an offscreen target before aligning it. Expanded execution details and edit boxes retain the same component instances outside the main window. List position/count attributes expose the original message positions. A persistent “显示全部消息以便查找” control reveals all history for native find or selection, and Ctrl/Cmd+F also enables it; “恢复按需显示” restores windowing around the same content. Long-history rows skip entrance animations so remounting and mode changes do not shift the reader.

`npm run benchmark:chat` measures synthetic 1,000/5,000-message conversations in desktop and narrow-screen Chromium, using the same in-memory API as browser regression. It reports mount time, streaming/scroll frame intervals, synthetic input-to-frame latency, mounted-message counts and Markdown DOM publications under `screenshots/performance/`. Its development-only fixture uses Vue's DOM component metadata to call the exposed navigation API and exercise editing, retry boundaries, expanded execution details, dynamic height, full-history find and bottom following. This is a development-build diagnostic rather than a production INP measurement. See [chat-performance.md](chat-performance.md) for the workload, limitations and comparisons. Short variants in `screenshot:smoke` check final-text, cursor, code-copy and reading-position correctness without timing thresholds.

## Provider Browser Regression

`screenshot:smoke` covers inline Provider creation on desktop and mobile, endpoint/model editing followed by reload, deletion, and model test results. Each of these scenarios intercepts all `/api/` calls with an isolated in-memory API; mutations and model tests never reach a real Provider or backend. The same fixture verifies fallback warnings on desktop/mobile and their removal after an explicit model selection.

## Shell Layout

The chat shell is three columns on a single background: the sidebar (collapsed state persisted under `sidebarCollapsed`, width `--sidebar-width`), the conversation card, and the run workbench card. Only the conversation and the workbench are cards — the sidebar deliberately paints no surface of its own, so it reads as part of the window background. The shell keeps a `--shell-gap` (the smallest spacing step) padding on all sides, and the seam between the conversation card and the workbench is the workbench's own resize handle, so the two cards are separated by exactly that gap. Below the 900px overlay breakpoint the sidebar becomes a drawer, the shell drops its padding, the conversation card goes full-bleed, and the workbench becomes a right-side drawer instead of a third column.

The conversation card header carries the session title, the session menu immediately after it, and the session context summary; its right side holds nothing but the workbench entry, and that entry exists only while the panel is collapsed. Once the panel is open its own header owns the collapse button, so no two buttons ever toggle the same panel. The collapsed state is not persisted, while the dragged width is (`runWorkbenchWidth`, clamped so the conversation card keeps a usable minimum). The workbench tab strip holds the `overview` tab plus one tab per opened participant, and the run overview itself — agents, goal, background tasks — lives in that `overview` tab rather than in a header capsule.

## Participant Threads

The conversation column always renders the root conversation. A sub-agent (participant) thread is rendered only in the run workbench: `workbenchTab` is either `overview` or a participant id, and `selectedParticipantId` is derived from it, so the participant list, the workbench tab and the delegation rows in the execution timeline all name the same focus. `messages` is the root list; a participant's own list is reached through `workbenchThreadMessages`.

Opening a participant is an explicit user action — the workbench overview's agent list, or the delegation row's detail in the execution timeline. It opens (or activates) that participant's tab and loads its history once, silently and with `viewEffects: false` so the conversation column's loading state, scroll and focus stay untouched; a thread that already has content is not refetched, since live events keep it current. Messages edited or rolled back are always root messages, because rollback semantics do not exist for a sub-agent thread.

A participant thread's live projection hangs off the run's input boundary: the user row that opened the run. Every execution envelope carries that boundary's message id, and `useMessageExecution` only projects an envelope once a matching user message exists in the participant's list — envelopes that arrive before it wait in a per-run queue. The backend therefore announces that boundary on the wire for both shapes of child run start: a mailbox-shaped initial message (a parent message starting or continuing a child run) arrives as `agent_message` addressed by `target_child_agent_id`, while a delegated task's synthetic instruction — which is deliberately not an agent message — arrives as a `state_sync` / `message_saved` user ref stamped with the participant id. Both land in the participant's thread only: the root column drops any `message_saved` ref carrying a child identity, so a sub-agent's input can never appear in the conversation column, and a session reload renders the same rows from history.

## Session Browser Workspaces

The composer's project dropdown includes an “添加项目” action below the searchable list. It closes the dropdown and opens the same `WorkspaceCreateDialog` used by the sidebar. Both entries register an existing local folder through the workspace store; successful creation selects that workspace and updates the composer's project path. Desktop users can browse for a folder, while browser users enter its absolute path.

Session list and workspace preview responses include `runtime_state`, derived from lightweight batched database reads using the same lifecycle rules as the full runtime snapshot. The sidebar shows a spinner for running/resuming sessions. The active session uses WebSocket snapshots; visible groups and pinned sessions refresh through `POST /sessions/states` every ten seconds while the page is visible (up to 200 IDs per batch). State queries use the same tenant and visibility restrictions as the session list and never load execution events.

Both SQLite and PostgreSQL apply the existing session metadata hydration before projecting batch states, matching full runtime reads for empty or non-object metadata. SQLite list pages support the API's 200-session limit so a complete status batch is returned after access filtering.

Pins are local preferences scoped to the tenant and user. Only normalized, unique session IDs are persisted; list responses restore their content through the `session_ids` filter. Pins appear in one section above both views and are excluded from their original groups, without changing workspace membership. Source/workspace filters still apply. Removing or losing access to a pinned session cleans up its ID on restoration. Project and pinned items reserve a fixed left icon slot: running sessions show a 14px spinner, idle sessions keep an empty placeholder, and hover/focus replaces the spinner with the pin action. This slot aligns the indented titles. Timeline status appears immediately before the time. Hover/focus hides the time and running indicator and reveals the delete action on the right.

Each tenant/user can pin up to 20 sessions across both views and all filters. Attempts beyond the limit only show a warning and preserve existing pins; unpinning is an explicit user action. Restoration requests contain at most 20 IDs and split long encoded ID filters to stay within the proxy request-line limit.

Pin restoration tracks per-session cache revisions. A response cannot overwrite title, message, or activity updates received after its request started, and missing IDs cannot undo newer pin changes. This also protects pinned sessions outside the currently loaded list page.

Timeline items have no leading icon slot: hover/focus replaces the runtime indicator and time with a pin button to the left of delete. Both actions use 20px buttons with 14px icons, and the pin button keeps a transparent background with feedback on the SVG itself. Hover transitions combine a short slide and scale for the action buttons with a fade of the time and runtime indicator. The fixed slots keep titles aligned throughout the transition; reduced-motion preferences disable these transitions.

The project view is built from the active workspace list, while the timeline is built from session history. Removing a project with sessions soft-removes its workspace registration: the project and its sessions disappear from the project view, but the sessions and their workspace metadata remain available in the timeline. Adding the same canonical local path reactivates the existing workspace ID, which restores those sessions in the project view without rewriting session records. A workspace with no sessions is deleted outright so unused registrations do not accumulate.

## Host Tools

The browser declares and executes `get_client_env`, which reports client-only environment data such as timezone, language, browser User-Agent, and screen size.

## Rendering Boundaries

- Pending follow-ups support take-back and deletion while the backend reports `can_manage`. DELETE compares the displayed original content and atomically expires both the unclaimed mailbox input and its durable receipt; consumed or concurrently changed inputs return a conflict. Cancellation is persisted as `cancelled` and does not appear as a send failure. "Edit" takes the input back and refills the composer with its original text for a fresh send. In-flight reads started before a mutation cannot overwrite its result.

- WebSocket sends persist a receipt before the early ACK. `GET /sessions/:sessionId/message-requests` returns pending receipts plus explicitly requested IDs, with processing, queued, consumed or failed state. The frontend queries on connect and while it has pending sends, restores pending rows after a reload, and reloads root history when consumption was missed. Failed receipts clear their pending row even if the original socket error was lost. Temporary query failures retain the content for the next reconciliation; completed request IDs prevent stale HTTP responses from resurrecting a row.

- Follow-up sends appear as compact single-line rows attached to the top of the composer while sending or waiting to enter context, with delivery status on the right and long text truncated. The queue stays visible above pending approval or user-input panels when they replace the composer. The store keeps this queue by session and request ID; an ACK ends the transport request, while the canonical consumed user message (or history reconciliation after reconnect) removes its pending row. Disconnecting, switching sessions, or disposing the view marks outstanding rows as unconfirmed and preserves their content, because asynchronous failures may have been missed. Late ACKs cannot restore a confirmed waiting status; explicit failures and consumption facts reconcile their own session even when it is inactive. Unconfirmed messages are never automatically resent. Root user consumption has one writer in the session dispatcher, including late replay after a run has finished. Buffered execution events wait for their exact message boundary.
- Execution panels belong to user message boundaries that have actual reasoning or tool steps. Consecutive inputs consumed by the same run do not each get an empty panel. History availability uses the same explicit `boundary_message_id` (or legacy sequence fallback within the run) as execution replay; live inputs gain a panel when execution events arrive, not when a run merely claims them. A run ID alone never overrides `has_execution: false` during loading or cache restoration.
- `VisualizationLoader.vue` handles chart, image, and generic file artifacts.
- `ImageLightbox.vue` uses Reka's modal dialog primitives for its full-screen preview, so previews opened from the attachment dialog participate in the same pointer-event and focus stack. Zoom buttons, wheel zoom, and dragging remain interactive above the attachment dialog; Escape closes only the preview, returns focus to its thumbnail, and leaves the attachment draft open. Opening a preview resets its transform. Previous/next buttons keep their position and size when pressed, so releasing the pointer cannot accidentally hit the dismissible background.
- Chat messages and Artifact selection do not auto-open a renderer or infer a presentation.

Image previews opt into `AuthenticatedImage`'s `retainWhileLoading` mode: the displayed source, transform, and object URL remain valid while the next image downloads and decodes offscreen. The source and default transform are replaced together only after decoding succeeds, with transform animation suppressed during the handoff; the previous object URL is released after the DOM update. Superseded downloads/decodes cannot overwrite the latest selection; failed loads preserve the displayed image, and closing the preview releases owned resources. Other image consumers keep their existing loading behavior.
