# 长会话性能基准

## 测量范围

基准通过现有 Chromium/CDP 冒烟工具驱动真实聊天组件，所有 API 都由场景独立的内存服务响应。不会创建真实会话、发送模型请求或修改用户配置。性能夹具仅由开发态脚本动态导入，不加入生产构建，也不向页面暴露调试接口。

固定负载：

- 1,000／5,000 条交替排列的用户/助手消息，部分历史消息含代码；分别运行桌面和窄屏四组场景。
- 末条助手消息初始约 11,770 字符，包含 100 个 JavaScript 代码块。
- 连续 90 帧追加文本，同时切换历史消息的悬停状态，每 10 帧向输入框派发一次输入事件。
- 用户预先向上滚动脱离吸附，追加期间校验阅读位置不漂移。
- 终态校验最终文本立即出现、流式光标移除、代码复制内容完整。
- 流式阶段结束后另采集 30 帧滚动数据，不混入流式阶段时序。

记录历史消息挂载时间、流式阶段帧间隔 P50/P95、输入事件到下一动画帧的 P95、Markdown DOM 更新次数、滚动帧间隔 P95、DOM 节点数和实际挂载消息数。挂载时间包含从空态进入消息列表的过渡。

## 运行方式

在仓库根目录执行 PowerShell 命令：

```powershell
$env:CHAT_PERF_LABEL = 'current'
npm -w frontend-client run benchmark:chat
```

脚本自动启动独立的 Vite 和无头 Chrome/Edge。`CHROME_BIN` 可指定浏览器；`SCREENSHOT_BASE_URL` 可复用已启动的开发服务器。`CHAT_PERF_LABEL` 区分每次报告，建议使用不同标签保留重复测量。报告写入被 Git 忽略的 `frontend-client/screenshots/performance/`，截图写入 `screenshots/smoke/`。

设置 `$env:CHAT_PERF_FULL_HISTORY = '1'` 可在同一实现、同一夹具中先启用“显示全部”，测量完整 DOM 的对照。恢复按需显示的基准前设为 `'0'`。`SCREENSHOT_SHOTS` 可筛选 `chat-performance-desktop`、`chat-performance-mobile` 及各自的 `-5000` 变体。计时对照请串行运行，避免同时执行构建或测试。

夹具 v3 等待尾部消息挂载及高度测量稳定，不再要求完整历史 DOM；增加挂载消息数统计、5,000 条负载和显示全部的对照开关。与早期 v1/v2 的计时不能交叉计算收益。按需显示场景在计时后继续检查 ID/seq/索引跳转、窗口外编辑草稿、全局重试边界、执行详情展开/收起、动态高度、新消息追加、底部跟随和原生查找模式切换。

## 首轮比较（2026-10-19）

同一本机 Windows、HeadlessChrome 154、Vite 开发构建，桌面为 1440×900，窄屏为 390×900。优化前为 `267f5446` 的聊天实现加上本次新增夹具。下表为首版相同夹具的各一次运行。后续夹具 v2 显式关闭 CSS 平滑滚动来设置阅读位置，并补充独立滚动采样；后续报告包含 `fixtureVersion: 2` 和 `readingPositionPx`，对比时必须使用相同夹具版本。

| 指标 | 桌面优化前 | 桌面优化后 | 窄屏优化前 | 窄屏优化后 |
| --- | ---: | ---: | ---: | ---: |
| 历史挂载（ms） | 1764.6 | 1228.8 | 1766.1 | 1290.1 |
| 流式帧间隔 P95（ms） | 209.0 | 70.9 | 282.5 | 83.0 |
| 合成输入到下一帧 P95（ms） | 279.3 | 155.8 | 301.6 | 152.6 |
| Markdown DOM 更新次数 | 91 | 35 | 91 | 42 |
| 阅读位置偏移（px） | 0 | 0 | 0 | 0 |

变更包括：一次预计算重试关联、用 ID 集合查询根消息成员身份，以及对流式追加采用 80ms 的展示更新窗口。最终文本与代码复制均完整，DOM 总数仍为 22,560，没有引入消息窗口化。

v2 完整性复核（优化后，单次运行）：桌面/窄屏流式帧间隔 P95 为 84.1/73.3ms，独立滚动帧间隔 P95 为 40.4/29.2ms；阅读位置分别位于 114,825/107,081px，追加期间偏移均为 0px，最终文本、光标和代码复制检查通过。它与首版夹具的定位行为不同，不与上表交叉计算收益。

这些结果用于确认优化方向，不代表所有设备的固定收益。窄屏运行仍在同一台电脑上，不能当作真实手机性能。输入事件由脚本派发，指标不是浏览器正式 INP；帧采样来自 requestAnimationFrame，也不能当作生产 FPS。对比时应固定浏览器、构建模式和负载，关闭其他重负载任务，并重复采样。

## 消息窗口化

主聊天列表达到 200 条可见消息后启用按需显示；同一会话持续保留这个模式，切换会话时重置。上下各保留 900px 预渲染区域，尾部两条消息保持挂载，以覆盖流式正文和正在执行的用户消息。编辑、展开、焦点所在消息额外保留在原位置。占位区域使用按稳定消息键缓存的高度；图片、Markdown、执行详情或窗口宽度变化后重新测量，并补偿阅读锚点。短会话和运行工作台的子线程维持完整渲染。

顶部“显示全部消息以便查找”和 Ctrl/Cmd+F 会挂载完整历史，方便浏览器查找和连续选择；“恢复按需显示”返回同一阅读位置。完整显示模式会恢复完整 DOM 的开销。消息列表同时提供 `scrollToMessage` 接口，用于挂载和定位窗口外的消息，原有引用点击事件继续沿组件树传递。

2026-10-19 同机串行对照（夹具 v3，`reference-full`／`reference-windowed` 报告，各组各一次；5,000 条窗口组补跑）。以下每格按“完整显示 → 按需显示”排列，完整显示是本次实现的对照模式，并非旧提交：

| 负载 | 整页 DOM 节点 | 历史挂载 ms | 流式帧间隔 P95 ms | 遍历全历史帧间隔 P95 ms |
| --- | ---: | ---: | ---: | ---: |
| 1,000 条／桌面 | 22,562 → 2,751 | 1405.7 → 517.8 | 49.8 → 29.8 | 18.5 → 64.1 |
| 1,000 条／窄屏 | 22,562 → 2,751 | 1374.3 → 531.5 | 49.8 → 31.9 | 17.8 → 65.4 |
| 5,000 条／桌面 | 101,962 → 2,751 | 5652.1 → 701.3 | 131.3 → 66.8 | 52.4 → 124.8 |
| 5,000 条／窄屏 | 101,962 → 2,751 | 5568.2 → 539.8 | 151.2 → 30.1 | 57.5 → 99.0 |

按需显示在尾部阅读时挂载 2 条消息，30 帧遍历采样中最多 27 条；完整显示挂载全部 1,000／5,000 条。整页 DOM 分别减少约 87.8%／97.3%，流式阶段阅读偏移均为 0px，最终文本、光标和代码复制检查通过。挂载与流式阶段改善明显，而大跨度遍历增加了创建行的成本；不据此声称所有滚动场景都更快。重复测量的计时有波动，DOM 数量与完整性断言更稳定。

## 后续边界

窗口化减少历史 DOM，并保留完整消息数据；没有减少历史下载量或单条长 Markdown 的解析范围。大量展开的消息也会增加挂载数。大跨度快速滚动需要创建新行，可能比已完整挂载的列表产生更高的单帧耗时；30 帧遍历全历史的滚动压力样本需单独解读，不等同于普通滚轮滚动。下一步可继续依据测量优化长正文解析与频繁挂载的成本。计时数据作为诊断报告，不设跨机器的硬性通过阈值；文本完整性、重试边界和滚动位置由测试守住。
